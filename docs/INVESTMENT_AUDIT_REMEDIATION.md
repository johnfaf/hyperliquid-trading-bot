# Investment audit: remediation and acceptance gates

**Decision: paper only.** This branch changes code, not the deployed release or any account. Passing tests shows that the covered behavior works in fixtures. It does not establish a trading edge or authorize the use of firm capital.

## Isolated crypto research

Use [the example environment](audit-paper-1000.env.example) with a new data volume and a separate process. Start it with no imported production environment, signer, partner credentials or Telegram control access. The listed paths and dashboard port are internal to that process. On a laptop without `/data`, point every path at a new research directory. Do not load the production config override or reset the existing book. Use local access or a private tunnel to the research dashboard.

Record the commit, dependency lock, data hashes/date ranges, strategy definition, fee/slippage assumptions, initial balance and model hashes (when used). Check `/api/ready` for `live_requested=false` and `signer_available=false`, and confirm the $1,000 balance on the new book before its first trade. Treat missing quotes and synthetic order-book data as research limitations. Use only base perp rates as defaults, not the exact rates of a particular account. See [Hyperliquid fees](https://hyperliquid.gitbook.io/hyperliquid-docs/trading/fees) and [funding](https://hyperliquid.gitbook.io/hyperliquid-docs/trading/funding).

Use `scripts/run_replay.py` with a frozen strategy snapshot, read-only candle cache, explicit time range and `--halt-on-error`. Keep the outbound network sandbox enabled. Save the command and report. The built-in smoke snapshot is a wiring test, not an investment benchmark. Run a second copy with worse spread/slippage and fee assumptions. Reject the claim of edge if it does not survive reasonable adverse costs and independent holdout testing.

## Incident and recovery drill

1. Pause new entries. Check venue positions and open orders independently of the bot. Cancel only identified entries and confirm that protection remains. Verify any pre-existing Hyperliquid `scheduleCancel` timer with the account operator; the new code does not arm one and cannot prove that a previously armed venue timer is gone. [Venue cancellation semantics](https://hyperliquid.gitbook.io/Hyperliquid-docs/for-developers/api/exchange-endpoint).
2. An emergency close is a separate reduce-only action. Do not retry an unknown submission as a fresh order. Verify actual fills and fresh positions; escalate any unresolved order, residual exposure, or missing protection. Do not use a restart or process shutdown as proof of safety.
3. Produce a consistent SQLite online backup, not a raw copy of a running WAL database. Record its SHA-256, ledger ID, timestamp and release ID; encrypt and transfer it to an independently administered destination. If using Postgres, back it up separately with its native tools.
4. Restore onto a clean isolated host and verify using `python scripts/verify_sqlite_backup.py PATH --sha256 ORIGINAL_DIGEST`. Then run the app's read-only DB audit against that restored copy. Record the elapsed time, last durable event, and any missing data; a checksum is not a venue reconciliation.
5. Verify that loss of the primary host still pages a human through independent monitoring. Test permissions, secrets recovery, rollback and a paper-only restart. Record the approvers and outcome.

### Import execution evidence offline

Archive the original [Hyperliquid fills JSON](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint) and its date range/source account. Obtain unaggregated records with exchange `time`, `tid` and `oid`. The endpoint has history limits; preserve overlapping exports and independently check coverage. Do not infer IDs from older summary CSVs.

`python scripts/import_hyperliquid_fills.py FILLS_JSON --ledger SEPARATE_DB --account PUBLIC_ACCOUNT_ADDRESS` uses no network or signer and refuses to write into the bot's ledger. Exact repeats are idempotent; same-key conflicting records fail the entire batch. Imported records do not establish completeness, ownership attribution, net returns or an approved ledger balance.

## Stock paper adapter acceptance contract

Choose one approved broker and one cash-equity account with a separate ledger and signer boundary. Accept versioned intents from research, but have a deterministic gateway enforce instrument allowlist, session and quote freshness, long-only, order caps, available **settled** cash and cash already reserved for pending orders. No leverage, shorting, derivatives, extended hours, or unattended order approval in the first pilot. A language model cannot bypass the gateway or hold trading credentials.

Require paper tests for session holidays/early closes and DST, halts, fraction/share increments, partial fills and duplicate events, lost acknowledgements and restarts, stale market data, settlement calendar, splits and dividends, and adverse overnight gaps. Persist client IDs before submission, deduplicate fill IDs, and block a resubmission while the last order is unknown. Archive independent broker statements. For a U.S. cash account, verify the broker's cash rules and [the SEC's T+1 guidance](https://www.investor.gov/introduction-investing/investing-basics/glossary/settling-securities-transactions-t1) before implementation.
